# プロジェクト憲法

この文書は、本プロジェクトのすべての作業者(人間・AIエージェント)が従う最上位の規則である。
CLAUDE.md、ADR、仕様、コードのいずれかがこの憲法と矛盾する場合は、この憲法が優先する。
この憲法の変更は、人間が承認した ADR によってのみ行う。

## 前提

- 本プロジェクトのコードは AI が書き、人間はコード差分をレビューしない。
- 人間がレビューするのは、仕様(受け入れ条件)、ADR、用語集(`CONTEXT.md` / `CONTEXT-MAP.md`)、この憲法である。
- したがって、コードの正しさは機械的なゲートで保証する。最終判定は GitHub Actions の CI で行う。

## 条文

### 第1条 仕様が唯一の正である
- システムの振る舞いは `openspec/specs/` の仕様で定義する。仕様にない振る舞いを実装してはならない。
- 仕様の変更は OpenSpec の変更提案(change)を通じてのみ行う。
- 要件には要件ID(例: `REQ-BOOKING-012`)を付け、受け入れ条件は EARS 形式で書く。

### 第2条 受け入れテストは不可侵である
- 受け入れテスト(`tests/acceptance/`)は、仕様から、実装より先に作成する。
- 実装フェーズの作業者は、仕様と受け入れテストを変更してはならない。テストが通らない場合は実装を直す。仕様やテストに誤りがあると考える場合は、作業を止めて人間に報告する。

### 第3条 テストを弱めてはならない
- `.skip` / `.only` / `.todo` の放置、アサーションの削除・緩和、テスト対象の差し替えによってテストを通すことを禁止する。
- カバレッジやミューテーションスコアの閾値を下げることを禁止する。閾値の変更には ADR を必要とする。

### 第4条 ゲートを迂回してはならない
- `git commit --no-verify`、強制プッシュ、ブランチ保護の回避を禁止する。
- `@ts-ignore`、`@ts-nocheck`、`any`、理由のない `eslint-disable` を禁止する。型エラーは型を直して解消する。
- ハーネス(hooks、CI、検査スクリプト、閾値設定)を変更する場合は、OpenSpec の変更提案と ADR を必要とする。

### 第5条 ユビキタス言語を使う
- 仕様、コード、テスト、コミットメッセージでは、`CONTEXT.md` に定義された用語を使う。
- 用語集にない概念が必要になった場合は、勝手に命名せず、用語の追加を提案する。

### 第6条 依存は外側から内側へ一方向に向ける
- モジュール間の参照は、各モジュールの公開窓口(`index.ts`)経由に限る。
- domain は外部に依存しない。application は domain にのみ依存する。
- 他モジュールのテーブルを直接読み書きしない。
- これらは dependency-cruiser で機械的に検査する。

### 第7条 金額と日時を正しく扱う
- 金額は整数の最小通貨単位と通貨コードで扱う。浮動小数を使わない。
- 日時はタイムゾーン込みで扱う。現地の日付(チェックイン日など)と UTC の時刻を混同しない。

### 第8条 外部依存はポートの向こうに置く
- 決済、メール、サプライヤー、時計、ID 生成などの外部依存は、ポート/アダプター構造で扱う。
- テストと E2E は外部サービスに依存せず、オフラインで安定して実行できなければならない。

### 第9条 すべての API ルートは認可ポリシーを宣言する
- 認可ポリシーの宣言がないルートは、型検査・起動時検査・テストのいずれかで失敗させる。

### 第10条 推測で決めない
- 仕様・ADR・この憲法で決まっていない判断が必要になった場合は、推測で進めず、選択肢と推奨案を示して人間に相談する。

## 開発プロセスの用語

業務の用語は `CONTEXT.md` に定義する。ここでは開発プロセスの用語だけを定義する。

| 用語 | 英語 | 定義 |
|---|---|---|
| 仕様 | spec | `openspec/specs/` にある、システムの振る舞いの定義。要件と受け入れ条件からなる |
| 変更提案 | change | OpenSpec で仕様・設計・タスクの差分をまとめたもの。`openspec/changes/` に置く |
| 要件ID | requirement ID | 要件を一意に識別する ID。`REQ-<コンテキスト>-<3桁の連番>` の形式 |
| 受け入れテスト | acceptance test | 要件IDを参照し、仕様の受け入れ条件を検証するテスト。`tests/acceptance/` に置く |
| ゲート | gate | CI で実行され、失敗すればマージを阻止する機械的な検査 |
| ハーネス | harness | ゲート、hooks、検査スクリプト、閾値設定など、品質を機械的に保証する仕組みの総称 |
| Grilling | grilling | 変更提案の作成前に、AI が人間に質問を重ねて計画と用語を詰める対話 |
| 役割 | role | 作業者の担当。spec-author(仕様作成)、test-author(受け入れテスト作成)、implementer(実装)、reviewer(レビュー) |
