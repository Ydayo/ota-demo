# ADR-0017: 保護対象への書き込みのローカルの確認をやめ、PR のレビューと CI で守る

- 日付: 2026-09-27
- 関連: ADR-0016 の「ローカル(早期フィードバック)」のうち、保護対象への書き込みを確認ダイアログで確認する決定を置き換える

## 背景

ADR-0016 では、保護対象(仕様・用語集・ADR、受け入れテスト、ハーネス、憲法)への書き込みのたびに、PreToolUse hook が Claude Code の確認ダイアログを出すことにした。フェーズ0の CI とハーネスの構築では、ハーネスのファイルを1つ書くたびにダイアログが出て、人間の確認の手間が大きすぎた。人間はダイアログの内容を毎回読むよりも、PR でまとめて確認することを選んだ。

## 決定

- PreToolUse hook は、保護対象への書き込みで確認ダイアログを出さない(`permissionDecision: "ask"` を返さない)。
- 次の拒否(deny)は残す(ADR-0016 のとおり)。
  - `~/.claude/` への書き込み
  - ゲートの迂回(`--no-verify`、強制 push、Bash からの `claude` の起動、`gh auth`)
- 保護対象は、次の3つで守る。
  - 人間の PR のレビュー(保護対象の変更は PR で確認する)
  - CODEOWNERS とルールセット(保護対象の変更には @Ydayo の承認が必要。ADR-0007)
  - CI の PR の分離の検査(実装の PR は仕様・用語集・ADR・憲法と受け入れテストを変更できない。ADR-0016)
- 保護対象の分類(`tooling/harness/src/hooks/protected-paths.ts`)は、CI の PR の分離の検査と、CODEOWNERS との一致の検査で引き続き使う。
- CI の検査内容を左右する `package.json`(各パッケージのものを含む)、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、各パッケージの `tsconfig.json` は、保護対象に加えない。これらの変更は PR のレビューで確認する(下記「結果」の受け入れたリスク)。

## 検討した選択肢

- 確認ダイアログを続ける(ADR-0016 のまま): 誤った書き込みにその場で気づけるが、ハーネスの構築や仕様の作成でダイアログが多すぎ、確認が形骸化するため不採用。
- 確認ダイアログに加えて、CI の PR の分離の検査と CODEOWNERS もやめる: PR のレビューだけに頼ることになり、実装の PR で受け入れテストを弱める変更を機械的に止められなくなるため不採用。
- 迂回の拒否も含めて PreToolUse hook を外す: `--no-verify` などのゲートの迂回を止められなくなるため不採用。
- `package.json` や `tsconfig.json` も保護対象に加える: CI の中身(scripts や型チェックの設定)の改変を CODEOWNERS で必ず人間に通せるが、人間は PR のレビューで確認するとしたため不採用。

## 結果

- 保護対象への書き込みで作業が止まらなくなる。
- 誤った書き込みに気づくのは PR の段階になる。実装の PR で仕様や受け入れテストを変えることは、引き続き CI によってできない。
- 受け入れたリスク: 実装の PR で `package.json` の scripts(`"lint": "true"` など)や、各パッケージの `tsconfig.json`(`strict: false` など)を変えると、CI の検査を弱められる。これらは CODEOWNERS の対象外であり、PR のレビューで人間が確認する。
- 受け入れたリスク: `.claude/settings.json` と `tooling/harness/src/hooks/` も確認なしで書き込めるため、AI は hook や deny ルールを書き換えてから迂回の操作(`--no-verify` など)を行える。ADR-0006 のとおり hook は迂回できる早期フィードバックであり、最終防衛線は CI、CODEOWNERS、ルールセットである。これらの書き換えは PR のレビューで人間が確認する。
- `package.json` と `pnpm-lock.yaml` は実装として扱うため、受け入れテストの PR では依存を追加できない。受け入れテストに新しい依存が必要な場合は、先に依存を追加する実装の PR を作る。
