# ADR-0003: DDD の実装スタイルは関数と型を中心とする

- ステータス: 承認済み(PR #1)
- 日付: 2026-09-27

## 背景

全モジュールで統一する DDD の実装スタイルを決める必要がある。要件として、予約の状態遷移をコンパイル時に検査すること、domain 層を外部依存ゼロに保つこと、プロパティベーステストとミューテーションテストで厚く検証することがある。

## 決定

関数と型を中心としたスタイルを採用し、Decider パターンの「状態を変える関数はドメインイベントを返す」考え方を取り入れる。

- 値オブジェクト: branded type と、生成用の関数(スマートコンストラクタ)で表す。生成関数は `Result<T, E>` を返し、不正な値は生成できない。
- 集約: readonly なデータ型と、それを操作する純粋関数の組で表す。状態を変える関数は、新しい集約と発生したドメインイベントを返す。
- 状態遷移: 状態ごとに型を分けた判別共用体で表す。遷移関数の引数の型で遷移元を制限し、不正な遷移をコンパイルエラーにする。
- リポジトリから読み込んだ集約は状態が不明なため、境界で実行時に状態を判定(型の絞り込み)してから遷移関数に渡す。
- 業務上のエラーは例外にせず `Result` で返す(ADR-0009)。
- 公開範囲は、クラスの private ではなく、モジュールの export で制御する。

例:

```ts
type PaidBooking = Readonly<{ kind: 'paid'; id: BookingId /* ... */ }>;
type ConfirmedBooking = Readonly<{ kind: 'confirmed'; id: BookingId; confirmedAt: Instant /* ... */ }>;

const confirm = (
  booking: PaidBooking,
  now: Instant,
): { booking: ConfirmedBooking; events: readonly [BookingConfirmed] } => ...
```

## 検討した選択肢

| 選択肢 | 不採用の理由 |
|---|---|
| クラス中心 | 不正な遷移を実行時の例外でしか防げない。可変状態になりやすい |
| 状態を型引数で表すクラス | `this` 型などの技巧が必要で、AI の書き方がぶれやすい |
| Effect | domain に外部ライブラリが入り、「domain は外部依存ゼロ」の方針と衝突する |
| Decider パターン(純粋形) | 状態の判定が実行時の分岐になり、コンパイル時の遷移検査が弱い。イベントを返す考え方のみ採用した |

## 結果

- 状態遷移の誤りをコンパイル時に検出できる。
- 集約がプレーンなデータになるため、Drizzle での永続化とプロパティベーステストが容易になる。
- カプセル化がクラスより弱いため、集約の内部データを直接組み立てることを lint(または型の工夫)で制限する方法を、フェーズ1で検討する。
