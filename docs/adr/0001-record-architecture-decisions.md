# ADR-0001: 設計判断を ADR として記録する

- ステータス: 提案中
- 日付: 2026-09-27

## 背景

本プロジェクトはコードを AI が書き、人間はコード差分をレビューしない。人間が設計に関与できる主な手段は、設計判断の記録をレビューすることである。判断の理由が残っていないと、後から AI が同じ議論を繰り返したり、過去の判断と矛盾する変更を行ったりする。

## 決定

- 設計判断は ADR(Architecture Decision Record)として記録する。
- 置き場所は影響範囲で分ける。
  - 複数のコンテキストやシステム全体に関わる判断(アーキテクチャ、ハーネス、技術選定、コンテキストの追加・分割・統合、コンテキスト間の連携方式): リポジトリルートの `docs/adr/`
  - 1つのコンテキストで閉じる判断(集約の境界、状態遷移、業務ルールの解釈): `packages/modules/<コンテキスト>/docs/adr/`
- ファイル名は `NNNN-<英語の短い説明>.md`(置き場所ごとに 0001 からの連番)とする。
- 各 ADR は「背景」「決定」「検討した選択肢」「結果」の節を持つ。外部ツールの仕様に依存する判断では「出典」の節を設け、一次情報の URL と確認日を記載する(憲法 第11条)。
- ステータスは「提案中」「承認済み」「却下」「置き換え済み(ADR-NNNN)」のいずれかとする。人間が承認するまで「提案中」とする。
- 承認済みの ADR は書き換えない。判断を変える場合は新しい ADR を作り、古い ADR のステータスを「置き換え済み」にする。
- ADR は原則として OpenSpec の変更提案を作る過程(Grilling)で作成する(ADR-0005)。フェーズ0の初期 ADR のみ、ハーネスが存在しないため例外的に直接作成する。

## 検討した選択肢

- 設計判断を記録しない / 設計書にまとめる: 判断の理由と時点が追えないため不採用。
- すべての ADR をルートに置く: コンテキスト固有の判断が埋もれ、コンテキストの独立性も表現できないため不採用。

## 結果

- 人間は ADR のレビューで設計に関与できる。
- ADR はロック対象(ADR-0006)とし、実装役の AI は変更できない。
